The Application
What is BoardUniverse?
A Spring Boot web application where users can browse, add, and review tabletop board games. Think of it like an online library catalogue — but for board games.
👤 Guest (No Login)
Can browse the full list of board games. Cannot add, edit, or review anything. Just a viewer — like a library visitor who can look at shelves but not borrow books.
🎮 Collector (User Role)
Logged in as bugs / bunny. Can add new board games to the catalogue and write reviews for existing ones. Like a librarian who adds books and writes summaries.
👑 Manager (Admin Role)
Logged in as daffy / duck. Can do everything the Collector can, plus delete games and moderate reviews. Like the head librarian.
🛠️ Tech Stack
Backend: Spring Boot 2.5.6 + Java 17
Templates: Thymeleaf server-side rendering
Security: Spring Security (role-based login)
Database: H2 in-memory (auto-creates on start)
Build Tool: Apache Maven 3
Testing: JUnit 5 + JaCoCo coverage
ORM: Spring Data JPA + JDBC
🎯 Real-World Analogy
Imagine a restaurant menu app. Guests can see the menu. Waiters (Collectors) can add new dishes. The chef (Manager) can remove bad dishes. Our app does the same — but for board games.
The Problem
Why do we need DevOps?
Without DevOps, every deployment is a manual, error-prone process. DevOps automates the boring, repetitive work so developers can focus on writing code.
❌ Without DevOps
Developer writes code → manually compiles → manually tests → manually builds JAR → manually copies to server → manually runs. Takes hours, breaks often.
"It works on my machine" — a developer says while production is down. No security scans, no code quality checks, no consistency.
🏠 Analogy
Like building a house by hand, brick by brick, with no blueprints. Every time you rebuild, the walls are slightly different.
✅ With DevOps
Developer pushes code → Jenkins automatically compiles → tests → scans for bugs → scans for security → builds Docker → deploys. Takes minutes, never forgets a step.
Every single build goes through the exact same 12 checkpoints. Consistent, reliable, and secure — every time.
🏭 Analogy
Like a factory assembly line. Every product goes through the same stations in the same order, and quality inspectors check at every step.

Stages 1 – 3
Checkout, Compile & Test
📥 Stage 1: Git Checkout
Jenkins connects to our GitHub repository and downloads all the latest code. The command checkout scm means "pull whatever branch triggered this build".
// Jenkinsfile
stage('Git Checkout') {
  steps { checkout scm }
}
⚙️ Stage 2: Compile
Maven reads pom.xml (our project recipe), downloads all dependencies (Spring Boot, Thymeleaf, etc.), and compiles 9 Java source files into bytecode (.class files).
stage('Compile') {
  steps { bat 'mvn compile' }
}
🧪 Stage 3: Test
Runs JUnit 5 unit tests to verify the code works correctly. JaCoCo measures test coverage — what percentage of our code is actually tested. If any test fails, the entire pipeline stops here.
stage('Test') {
  steps { bat 'mvn test' }
}
// Uses JaCoCo plugin (v0.8.12)
🍳 Kitchen Analogy
Checkout = getting the recipe from the cookbook.
Compile = gathering and prepping all ingredients.
Test = tasting the dish before serving it to check if the flavour is right. If it's bad, you stop and fix it — you don't serve it.
Stages 4 – 6
Security Scan & Code Quality
🛡️ Stage 4: Trivy Filesystem Scan
Trivy is an open-source security scanner by Aqua Security. Here it scans our project files and dependencies (pom.xml, JARs) for known vulnerabilities (CVEs). Generates an HTML report: trivy-fs-report.html
// Actual command from Jenkinsfile
trivy.exe fs \
  --format template \
  --template "@trivy-html.tpl" \
  --output trivy-fs-report.html .
🏥 Analogy
Trivy is like an X-ray machine at airport security. It scans everything inside your suitcase (code) to find anything dangerous (vulnerabilities) before you board the plane (go to production).
🔍 Stage 5: SonarQube Analysis
SonarQube (running on port localhost:9000) performs static code analysis — it reads your source code without running it and checks for bugs, code smells, duplications, and security hotspots.
sonar-scanner \
  -Dsonar.projectName=BoardUniverse \
  -Dsonar.projectKey=BoardUniverse \
  -Dsonar.java.binaries=target/classes
✅ Stage 6: Quality Gate
After SonarQube analyses the code, it gives a pass/fail verdict called a Quality Gate. Jenkins waits up to 1 hour for this result. If the code quality is below the threshold, we know before deploying.
waitForQualityGate abortPipeline: false
// timeout: 1 hour max wait
Stages 7 – 8
Package & Publish to Nexus
📦 Stage 7: Build Package
Maven packages our compiled code, resources, and dependencies into a single executable JAR file: database_service_project-0.0.5.jar. The -DskipTests=true flag means "skip tests again, we already ran them in Stage 3."
stage('Build Package') {
  steps { bat 'mvn package -DskipTests=true' }
}
// Output: target/database_service_project-0.0.5.jar
📬 Analogy
Stage 7 is like boxing up a product (the JAR file). Stage 8 is like shipping it to a warehouse (Nexus). Now anyone on the team can go to Nexus and download version 0.0.5 whenever they need it — no need to rebuild.
☁️ Stage 8: Publish to Nexus
Nexus Repository Manager (port localhost:8081) is a private artifact warehouse. We upload our JAR here so it's versioned and backed up. Even if our code changes, version 0.0.5 is always preserved.
nexusArtifactUploader(
  nexusVersion: 'nexus3',
  nexusUrl: 'localhost:8081',
  repository: 'boardgame-releases',
  groupId: 'com.javaproject',
  version: '0.0.5',
  artifacts: [[
    artifactId: 'database_service_project',
    file: 'target/...0.0.5.jar',
    type: 'jar'
  ]]
)
Stages 9 – 10
Docker Build & Image Scan
🐳 Stage 9: Docker Build
Docker reads our Dockerfile and creates a container image. We use a multi-stage build — two stages in one file:
# Stage 1: Build (has Maven + full JDK = ~800 MB)
FROM maven:3.9.9-eclipse-temurin-17 AS build
COPY pom.xml .
RUN mvn dependency:go-offline
COPY src ./src
RUN mvn clean package -DskipTests

# Stage 2: Run (only JRE Alpine = ~150 MB)
FROM eclipse-temurin:17-jre-alpine
RUN addgroup -S appgroup && adduser -S appuser
COPY --from=build /app/target/*.jar app.jar
USER appuser
ENTRYPOINT ["java", "-jar", "app.jar"]
🔐 Security Features in the Dockerfile
Multi-stage build: The final image doesn't contain Maven, source code, or build tools — only the JAR. Smaller image = smaller attack surface.

Non-root user: USER appuser means the app runs as a restricted user, not root. Even if someone hacks the container, they have limited permissions.

Alpine base: Uses Alpine Linux (~5 MB) instead of Ubuntu (~70 MB). Fewer packages = fewer potential vulnerabilities.
🔒 Stage 10: Trivy Image Scan
After building the Docker image, Trivy scans it again — this time checking the container layers, OS packages, and runtime libraries. Report: trivy-image-report.html
Stages 11 – 12
Push to DockerHub & Deploy
🚀 Stage 11: Docker Push
The built image is pushed (uploaded) to DockerHub — a public container registry. Our image lives at manish26m/boardgame:latest. Anyone can pull and run it.
withDockerRegistry(credentialsId: 'docker-cred') {
  bat "docker push manish26m/boardgame:latest"
}
🌐 Stage 12: Deploy
Jenkins stops and removes the old container (if any), then starts a fresh one from the new image. The app is mapped to port 8085 on the host machine.
// Stop old, remove old, run new
bat 'docker stop boardgame || ver > nul'
bat 'docker rm boardgame || ver > nul'
bat "docker run -d -p 8085:8080 \
  --name boardgame manish26m/boardgame:latest"
📧 Post-Build: Email Notification
After all 12 stages (pass or fail), Jenkins sends a detailed HTML email to manish.mishra2605@gmail.com with build status, duration, and the Trivy scan reports attached.
post { always {
  emailext(
    subject: "[SUCCESS] BoardUniverse - #42",
    to: 'manish.mishra2605@gmail.com',
    mimeType: 'text/html',
    attachmentsPattern:
      'trivy-fs-report.html,
       trivy-image-report.html'
  )
}}
🏗️ Analogy
Stage 11 = uploading your recipe to a cloud cookbook (DockerHub). Stage 12 = cooking and serving the dish (running the container). The email = sending a status report to the head chef saying "dish is ready" or "something went wrong."

The orchestrator. Reads our Jenkinsfile and executes all 12 stages in order. Uses JDK 21 and Maven 3 tools. Runs on Windows (uses bat commands, not sh).
📊

localhost:9000
Static code analyzer. Runs inside a Docker container (sonarqube:lts-community). Checks for bugs, code smells, duplications, and security hotspots. Provides the Quality Gate verdict.
📦

Private artifact warehouse. Runs as Docker container (sonatype/nexus3). Stores versioned JAR files. Repository name: boardgame-releases.

localhost:8085 → 8080
The final deployed application. Runs inside Docker as non-root user. Host port 8085 maps to container port 8080. Image: manish26m/boardgame:latest.
Containerization
Dockerfile Deep Dive
# ─── Stage 1: BUILD (heavy, ~800MB) ─── FROM maven:3.9.9-eclipse-temurin-17 AS build WORKDIR /app # Copy pom.xml first → Docker caches this layer # If pom.xml didn't change, skip re-downloading COPY pom.xml . RUN mvn -B -q -DskipTests dependency:go-offline # Now copy source code and build the JAR COPY src ./src RUN mvn clean package -DskipTests # ─── Stage 2: RUN (lightweight, ~150MB) ─── FROM eclipse-temurin:17-jre-alpine WORKDIR /app # Create non-root user for security RUN addgroup -S appgroup && adduser -S appuser -G appgroup # Copy ONLY the JAR from Stage 1 (not Maven/src) COPY --from=build --chown=appuser:appgroup \ /app/target/*.jar app.jar EXPOSE 8080 USER appuser ENTRYPOINT ["java", "-jar", "app.jar"]
🎯 Why Multi-Stage?
Stage 1 has Maven + full JDK (~800 MB) — only needed for building. The final image only has JRE (~150 MB) — just what's needed to run. 80% smaller final image.
🔑 Why dependency:go-offline first?
Docker caches each layer. If pom.xml didn't change, Docker skips re-downloading ~50 dependencies. Only the source code layer rebuilds. Saves 2-3 minutes per build.
👤 Why non-root user?
If an attacker breaks into the container, they can only do what appuser can do — which is very little. They can't install software, modify system files, or access the host machine.
🏔️ Why Alpine?
Alpine Linux is only ~5 MB. Ubuntu is ~70 MB. Fewer pre-installed packages means fewer things that can have vulnerabilities. Less surface area to attack.
Kubernetes
Container Orchestration
Our project also includes a Kubernetes manifest (deployment-service.yaml) for production-scale deployment with auto-scaling and load balancing.
apiVersion: apps/v1 kind: Deployment metadata: name: boardgame-deployment spec: replicas: 2 # Run 2 copies of the app selector: matchLabels: app: boardgame template: spec: containers: - name: boardgame image: manish26m/boardgame:latest imagePullPolicy: Always ports: - containerPort: 8080 --- apiVersion: v1 kind: Service metadata: name: boardgame-ssvc spec: type: LoadBalancer ports: - port: 80 targetPort: 8080
🔄 Deployment (replicas: 2)
Tells Kubernetes to run 2 identical copies of our app. If one crashes, the other keeps serving users while Kubernetes automatically restarts the failed one.
⚖️ Service (LoadBalancer)
A LoadBalancer Service distributes incoming user traffic evenly between the 2 replicas. Users access port 80, which routes to container port 8080 internally.
📥 imagePullPolicy: Always
Every time a pod restarts, it always pulls the latest image from DockerHub. This ensures deployments always use the newest code.
🍕 Analogy
Deployment = Having 2 pizza ovens instead of 1. If one breaks, the other keeps baking. Service = The counter person who sends orders to whichever oven is free. LoadBalancer = Fair distribution of orders.
